# EgoFlow App Project Guide

`ego-flow-app`은 `glasses → app → server` 흐름에서 **app 계층**을 담당하는 저장소다. Meta AI(DAT) glasses의 live preview를 보여주고, 사진을 찍고, live feed를 EgoFlow backend로 publish 한다. publish 경로는 세 가지 transport 중 하나를 고른다: **RTMP / WHIP / HTTP-chunk**.

세 transport 모두 본 저장소 안에 있다. slab-append → Clone-server 트랙만 sibling fork(Clone Glasses)로 분리되어 있고, `:core`의 `Transport` 인터페이스 seam을 공유하는 fork 전략으로 유지된다 (fork 위치: `samples/CameraAccessAndroid/README.md`의 "Sibling fork" 절).

Android 구현(`samples/CameraAccessAndroid`)은 다섯 개의 Gradle 모듈로 나뉜다.

- `:app` — Compose UI, `StreamViewModel`, foreground `StreamingService`, 설정, DAT/phone 소스 선택
- `:core` — `Transport` 인터페이스 + `TransportFactory` + 공유 `VideoEncoder`(MediaCodec H.264/HEVC) + YUV 변환
- `:transport-rtmp` — RTMP/RTMPS publish + `EgoFlowBackendClient`(공유 backend client) + auth/repo prefs
- `:transport-whip` — WHIP(WebRTC-HTTP Ingestion) publish
- `:transport-http` — fragmented-MP4 chunk 업로드 ingest

`:app`은 `:core`의 `Transport` 인터페이스에만 의존한다. 각 transport 구현은 자기 모듈 안에 봉인되어 있어, 같은 seam을 따라 다른 transport(예: fork의 slab-append)가 들어올 수 있다.

## 핵심 정리

- 현재 `glasses → app → server` 실제 Android 구현은 `samples/CameraAccessAndroid`가 기준이다.
- publish는 RTMP / WHIP / HTTP 세 transport를 Settings에서 고르며, 셋 다 같은 `EgoFlowBackendClient` 제어면(register → publish-ticket → close-intent)을 공유한다.
- RTMP/WHIP를 받는 MediaMTX 스택은 **외부 참조 스택**이며 더 이상 본 저장소에 vendoring 되지 않는다. 앱은 테스트 대상 backend/MediaMTX host를 가리키도록 설정한다.
- slab-append/Clone-server 트랙은 본 저장소에 없다. sibling fork인 Clone Glasses가 담당한다.
