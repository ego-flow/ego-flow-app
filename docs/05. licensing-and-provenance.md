# Licensing and Provenance Review

## Status

**Open — mixed-scope release risk accepted.** This document records provenance evidence; it does not grant a license or replace legal review. The unresolved rights block an MIT/OSI claim for the app repository, but the approved `v0.0.1` plan may retain the source only if it is clearly presented as source-available under the applicable upstream terms and excluded from EgoFlow's MIT claim.

Do not describe this repository as entirely MIT-licensed until the open questions below are resolved. The root `LICENSE` currently contains Meta Wearables Developer Terms rather than an OSI-approved license for EgoFlow's first-party code.

## Approved v0.0.1 release decision

- Use `ego-flow-app/main` as the app release candidate.
- Preserve `origin/extentos` exactly as-is; do not merge, modify, delete, or force-push that branch.
- Publish `ego-flow-server` and `ego-flow-py` as the MIT open-source components.
- Present `ego-flow-app` as a mixed, source-available component governed by the applicable Meta and other upstream terms.
- Exclude the app repository, Meta SDK, recorded sample code, and provenance-uncertain derivatives from every EgoFlow MIT or OSI-open-source claim.
- Preserve upstream notices and state that written redistribution permission remains unresolved.
- Keep the long-term independently authored MIT client as a follow-up objective rather than claiming it has already been achieved in `v0.0.1`.
- Retain the iOS Experimental directory as source reference only; exclude it from supported builds and the contest demonstration, and state that submitted Core artifacts do not call a runtime AI model.

## Intended outcome

- License EgoFlow-owned app code under MIT, consistently with `ego-flow-server` and `ego-flow-py`.
- Treat Meta Wearables SDK packages as proprietary external dependencies, not as EgoFlow or OSI-licensed code.
- Preserve all upstream copyright and notice obligations.
- Publish the whole `ego-flow-app` repository as OSI open source only after copied or adapted source has a compatible redistribution basis or has been independently replaced.

## Authenticated terms review

This is an engineering release decision, not legal advice. Section references below are to the
[Meta Wearables Developer Terms](https://wearables.developer.meta.com/terms) reviewed in the
account context recorded above.

- Section 2(a) grants only a limited, non-transferable, non-sublicensable, non-assignable, and
  revocable license to use the Technology for an Integration with Meta-approved products.
- Section 2(b)(i) permits modifying or using sample apps or sample source only when the
  documentation accompanying the Technology expressly authorizes it. This exception does not
  grant MIT relicensing rights.
- Section 2(b)(ix) prohibits removing or changing license terms, policy links, copyright notices,
  and related notices.
- Section 2(b)(x) prohibits using or redistributing the Technology in a way that would subject it,
  any portion of it, or Meta to an open-source license or other restrictions.
- Section 10(a) states that Meta or its licensors own the Technology, including sample apps,
  sample code, and all derivatives. EgoFlow retains rights only in its Integration excluding the
  Technology.
- Section 10(b) recognizes separately licensed third-party material, but no separate OSI license
  grant was found for the recorded Meta sample files.
- Section 13(a) allows Meta to terminate the license at its discretion. Section 13(c) then requires
  stopping use of the Technology and Integrations incorporating it and destroying or returning
  copies of the Technology and confidential information.

### Engineering conclusion

The reviewed terms do not provide a basis to redistribute the recorded Meta sample or derivative
source under MIT or another OSI-approved license. Public availability on GitHub and permission to
modify an authorized sample for an Integration are not permission to sublicense that source.

An MIT-licensed EgoFlow client may integrate with the separately supplied proprietary DAT SDK only
if the client contains independently authored EgoFlow code, keeps the SDK and Meta Technology out
of the MIT grant, preserves required notices, complies with the applicable documentation, and
passes Meta's Integration Review before general release. Written Meta permission would be required
to change this conclusion for copied or derivative sample source.

## Initial source-scope evidence

The repository's existing `THIRD_PARTY_NOTICES.md` declares both mobile samples to be adapted from the upstreams above. Local inspection found Meta copyright headers in 24 iOS files and 18 Android files.

### Android Core

Meta-header files cover approximately 3,676 lines and include the following high-impact areas:

- application and Gradle setup
- `MainActivity`
- `StreamViewModel` and `StreamUiState`
- wearable state and view models
- streaming and non-streaming Compose screens
- shared UI components and resources

Several additional Android files share names and structure with the recorded VisionClaw tree. A shared name is only a triage signal, not proof of copied expression. Each file still requires line-level or history-based review.

### iOS Experimental AI Reference

Every current Swift source basename was found in at least one of the recorded Meta iOS or VisionClaw trees. Gemini, OpenClaw, settings, audio, and phone-camera files align with the recorded VisionClaw scope; DAT views and view models align with both upstream trees.

Until rights are confirmed, treat the entire `samples/CameraAccess` source tree as derived or provenance-uncertain rather than EgoFlow-only MIT code.

### Assets and notices

Review icons, launcher images, test images, test videos, and the copied `NOTICE` independently from source code. Asset copyright and redistribution rights do not follow automatically from a source-code license.

It does not prove that each native subcomponent has a separate redistribution grant. Package-level license evidence and the Meta Android `NOTICE` remain authoritative, and Meta `mwdat-core`/`mwdat-camera` stay outside the EgoFlow MIT/OSI claim.

## Operational obligations surfaced by the review

These items will be handled in the privacy, security, and release-readiness phases. They do not
change the source-licensing conclusion above.

- Section 4 requires Meta Integration Review before an Integration is generally released and
  permits ongoing compliance monitoring.
- Section 5 limits Technology Data use to operating, supporting, maintaining, or improving the
  user-requested Integration and complying with law. It restricts sharing, requires proof of user
  direction or consent where applicable, imposes written obligations on service providers, and
  requires deletion in specified circumstances.
- Section 6 requires an accurate privacy policy covering data, processing, purposes, and deletion
  requests.
- Section 7 requires appropriate safeguards, a public vulnerability-reporting channel, prompt
  remediation, and notification to Meta of relevant security incidents.
- Any external AI processor receiving Technology Data must be assessed as a service provider under
  Section 5 before release; disclosure in an AI appendix or SBOM alone does not satisfy the data-use
  obligations.

## Long-term strict-OSI fallback

1. Preserve the recorded upstream revisions and applicable terms.
2. Treat the reviewed terms as insufficient for sample-source redistribution or MIT relicensing
   unless Meta supplies a separate written grant.
3. Classify each shipped file as `first-party`, `derived`, `external dependency`, or `asset`.
4. Apply MIT only where EgoFlow owns the relevant rights.
5. Independently reimplement the minimum Android Core flow from public SDK documentation and
   EgoFlow requirements.
6. Move the iOS Experimental AI Reference to a separate restricted lab repository.
7. Retain provenance records without copying restricted source into the MIT repository.

The minimum Android Core flow is registration, wearable or phone-camera acquisition, stream start, stream stop, and failure recovery. Reimplementation should use a new state model and UI rather than reproduce upstream file structure.

The approved `v0.0.1` mixed-scope release does not execute this fallback yet. It remains the path to a future app repository that can be presented as MIT/OSI open source without relying on unresolved sample-source rights.

## Not authorized yet

- Replacing the root `LICENSE` with MIT for the entire existing tree
- Removing upstream copyright headers
- Calling Meta SDK or the recorded sample code open source
- Shipping a release that claims complete OSI licensing
- Treating public GitHub access as permission to relicense
