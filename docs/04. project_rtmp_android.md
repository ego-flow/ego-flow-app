# CameraAccessAndroid — RTMP transport

이 문서는 `samples/CameraAccessAndroid`의 RTMP transport 구현을 정리한다. RTMP는 앱이 지원하는 세 transport(RTMP / WHIP / HTTP) 중 하나이며, 가장 성숙한 기준 구현이다. WHIP/HTTP는 같은 `Transport` seam과 `EgoFlowBackendClient` 제어면을 공유하므로 여기서 설명하는 backend 계약 대부분이 그대로 적용된다. 모듈 개요는 [03. project_architecture.md](./03.%20project_architecture.md) 참고.

## 1. 역할

`CameraAccessAndroid`는 다음을 담당한다.

- Meta Wearables DAT SDK를 통해 glasses 연결
- live video preview 표시 + phone-camera fallback
- photo capture
- EgoFlow backend 로그인 및 recording session 생성
- publish 직전에 publish-ticket를 받아 RTMP 또는 RTMPS로 publish
- 정상 종료 시 close-intent 전송, 실패/네트워크 유실 시 소켓만 닫음

즉 현재 `glasses -> app -> server` 실시간 경로의 Android 진입점이다.

## 2. 전체 흐름 (RTMP)

```mermaid
flowchart LR
    Glasses["Meta Glasses"] -->|DAT video stream| App["CameraAccessAndroid"]
    App -->|POST /api/v1/auth/app/login| Backend["EgoFlow backend"]
    App -->|POST /api/v1/streams/register| Backend
    App -->|POST /api/v1/streams/{id}/publish-ticket| Backend
    Backend -->|recording_session_id| App
    Backend -->|stream_path + publish_ticket| App
    App -->|RTMP publish| MediaMTX["MediaMTX (외부)"]
    App -->|POST /api/v1/recordings/{id}/close-intent| Backend
```

핵심:

- app은 register 응답으로 바로 publish하지 않고, publish 직전에 publish-ticket(TTL 60s)를 받아 RTMP URL을 조립한다.
- app이 다루는 단위는 일반 live session이 아니라 `recording_session_id`다.
- **owner-lease heartbeat와 자동 reconnect는 없다.** mid-stream 사망은 MediaMTX read/write timeout + hook이 감지한다. 실패 시 앱은 에러를 노출하고 device selection으로 돌아가며, 사용자가 명시적으로 재시도한다.

## 3. 모듈 구성

CameraAccessAndroid는 다섯 개의 Gradle 모듈로 나뉜다 (`settings.gradle.kts`). RTMP에 직접 관여하는 것은 `:app`, `:core`, `:transport-rtmp`다.

| 모듈 | 책임 |
| --- | --- |
| `:app` | UI, `StreamViewModel`, foreground service, 권한/DAT 초기화, 일반 app 설정, transport 선택 |
| `:core` | transport-agnostic 공통 — `Transport` 인터페이스, `TransportFactory`, codec/state 타입, video encoder, YUV 변환 |
| `:transport-rtmp` | RTMP/RTMPS 구현 + 공유 `EgoFlowBackendClient` + auth/repo prefs |

패키지 루트는 `io.egoflow.app`이다.

### 3.2 UI 레이어

`ui/`의 주요 화면: `StreamScreen`, `HomeScreen`, `MainTabScreen`, `LoginScreen`, `SettingsScreen`, `NonStreamScreen`, `MicDiagnosticsScreen`, `MockDeviceKitScreen` 등. 공유 컨트롤은 `PillButton`, `CircleButton`, `SwitchButton`, `ControlsRow`. 테마는 `ui/theme/{Theme,Color,Shape}.kt`.

`ui/repo/`는 RepoScreen을 컴포넌트 단위로 쪼갠 패키지다 (`RepoScreen`, `RepoController`, `components/*`).

아이콘은 `compose-icons-lucide`로 통일되어 있다. androidx material-icons 의존성은 사용하지 않는다.

## 4. 앱 시작 시 동작

`MainActivity`는 다음을 수행한다.

1. Android 권한 요청
2. `SettingsManager` 초기화
3. 화면 켜짐 유지
4. DAT SDK 초기화
5. wearables 모니터링 시작
6. Compose UI 표시

필요 권한: Bluetooth / Bluetooth Connect / Internet / Record Audio / Camera.

## 5. 스트리밍 제어 구조

`StreamViewModel`이 중심이다. transport 선택은 `SettingsManager.transportMode`로 결정되고, `buildTransport()`가 해당 factory를 골라 `Transport` 인스턴스를 만든다.

### 5.1 glasses mode

- DAT `StreamSession` 시작, video frame collect, preview bitmap 갱신, `Transport`로 frame 전달
- DAT session이 `STOPPED`가 되면 `stopStream`을 glasses-driven stop으로 처리

### 5.2 phone mode

- `PhoneCameraManager` 사용, phone camera I420 frame을 preview와 transport 전송에 사용

### 5.3 foreground service

스트리밍 중 `StreamingService`가 올라간다. foreground notification 표시, partial wake lock 획득(10분 timeout), background/screen lock 상태에서도 스트리밍 유지 시도.

## 6. backend 연동

세 transport가 공유하는 `EgoFlowBackendClient` 기준. 모든 호출은 동기식이며 `Dispatchers.IO`에서 실행된다. base URL은 `AuthPrefs.egoFlowApiBaseUrl`을 정규화해 `/api/v1`을 보장한다.

### 6.1 로그인

- `POST /api/v1/auth/app/login` — `AuthPrefs`의 `egoFlowUserId`/`egoFlowPassword` 전송, JWT token 획득
- 토큰은 list/register 호출 간 캐시되며 401 시 재로그인

### 6.2 repository 선택

- `GET /api/v1/repositories/maintain` — 사용자가 maintain 가능한 repository 목록 조회
- 선택된 repository id/name을 `RepoPrefs`에 저장

### 6.3 recording session 생성

- `POST /api/v1/streams/register`
- request: `repositoryId`, `deviceType`, `ingestType`(RTMP/WHIP은 `MEDIAMTX`, HTTP는 `HTTP`)
- response: `recording_session_id` (서버가 PENDING RecordingSession 생성/재사용)
- 응답에 `X-Refreshed-Token` 헤더가 오면 이후 요청에 즉시 반영
- 결과는 `RegisteredStreamSession(authToken, userId, recordingSessionId)`로 보관

### 6.4 publish ticket 발급

- `POST /api/v1/streams/{recordingSessionId}/publish-ticket`
- response로 `stream_path`, `publish_ticket`(TTL 60s)를 받아 최종 publish URL을 조립
- 결과는 `PublishTicketGrant(authToken, streamPath, publishTicket, publishUrl)`

### 6.5 RTMP publish

- publish URL: `rtmp://{host}:1935/{stream_path}?ticket={publish_ticket}` 또는 `rtmps://...`
- `ticket` query가 publish auth를 담당한다
- `RtmpPublisher`는 `rtmp://`와 `rtmps://`를 모두 허용한다. `rtmps://`는 기본 포트 `1936`, host-bound TLS socket, SNI/endpoint identification, hostname 검증을 사용

### 6.6 stop / close-intent

정상 종료(사용자 Stop 또는 glasses 종료)일 때만:

- `POST /api/v1/recordings/{recordingSessionId}/close-intent`
- 서버가 이 세션을 `NORMAL_DISCONNECT`로 기록

실패/네트워크 유실 시에는 close-intent를 생략하고 소켓만 닫는다 → 서버가 `UNEXPECTED_DISCONNECT`로 기록한다. STREAMING에 도달하지 못한 반쯤 만들어진 세션은 close-intent 대상이 아니므로 그대로 둔다.

> 예전 문서의 `/recordings/:id/stop`(USER_STOP/GLASSES_STOP body)와 owner-lease heartbeat, `STALE_PUBLISH_CONNECTION` 기반 reconnect는 더 이상 존재하지 않는다. 앱 내부 `StopReason`(USER_STOP/GLASSES_STOP/NETWORK_LOST/FATAL_ERROR)은 UI 문구/close-intent 여부를 정하는 데만 쓰인다.

## 7. 실패 처리

- transport 오류는 `classifyRtmpTransportFailure`가 retryable/non-retryable로 분류한다. 네트워크/timeout은 retryable, TLS handshake/hostname mismatch/auth 실패는 non-retryable.
- 다만 **앱은 자동 reconnect를 하지 않는다.** 실패는 `TransportState.Failed(reason)`로 올라오고, `StreamViewModel`이 스트림을 내리고 device selection으로 돌아간다. 사용자가 새로 시작하면 register부터 다시 시작한다.
- `RtmpDiagnostics`는 최근 이벤트를 유지하며 debug overlay(`SettingsManager.rtmpDebugOverlayEnabled`)로 노출된다. `publishUrl`의 `ticket`/`token`/`pass`/`authorization` 값은 자동 마스킹된다.

## 8. 설정 구조

설정은 세 저장소로 나뉜다.

### 8.1 `:app/settings/SettingsManager.kt`

app-wide 일반 설정. SharedPreferences `"egoflow_settings"`.

- `transportMode` — `RTMP` / `WHIP` / `HTTP` (기본 RTMP)
- `rtmpEnabled` (기본 true), `rtmpAudioEnabled`, `audioSource`(AUTO/GLASSES/PHONE), `rtmpCompressVideo`, `rtmpVideoCodec`(H264/HEVC), `rtmpDebugOverlayEnabled`
- `videoQuality`(LOW/MEDIUM/HIGH), `themeMode`(SYSTEM/LIGHT/DARK)

### 8.2 `:transport-rtmp/settings/AuthPrefs.kt`

EgoFlow backend 인증. EncryptedSharedPreferences `"egoflow_auth_secure"`.

- `egoFlowApiBaseUrl`, `egoFlowUserId`, `egoFlowPassword`, `rememberMe`, `authDisplayName`

`device_type`은 별도 저장 없이 런타임에 결정된다(phone/glasses 모드 매핑, `deviceTypeProvider`).

### 8.3 `:transport-rtmp/settings/RepoPrefs.kt`

선택된 repository. SharedPreferences `"egoflow_repo"`.

- `egoFlowRepositoryId`, `egoFlowRepositoryName`

## 9. 빌드 및 실행

```bash
cd ego-flow-app/samples/CameraAccessAndroid
./gradlew assembleDebug
```

실행 전 준비:

- Meta DAT Android Maven 의존성 접근용 GitHub classic PAT(`read:packages`)
- `local.properties`의 `github_token=...` 또는 `GITHUB_TOKEN` 환경변수
- `run.sh`가 JDK 17 `JAVA_HOME` 설정 + `GITHUB_TOKEN` export + 빌드를 감싼다

(예전의 `Secrets.kt`/`Secrets.kt.example`는 제거됐다. 런타임 backend/인증 설정은 앱 안에서 `AuthPrefs`/`RepoPrefs`에 저장한다.)

실기기에서 로컬 server를 붙일 때: host의 public HTTP 포트를 유지하고 device에서 `adb reverse`로 포트를 매핑한 뒤, 앱의 backend base URL을 해당 로컬 주소로 설정한다. RTMP/RTMPS/HLS도 필요 시 각각 `adb reverse`를 건다.

## 10. 이 샘플을 볼 때의 의미

이 샘플은 다음을 확인할 때 기준이 된다.

- DAT 기반 glasses live preview가 Android에서 어떻게 동작하는가
- Android가 backend가 발급한 publish-ticket로 어떻게 RTMP/RTMPS publish 하는가
- recording-session 기반 server 구조에서 app이 어떤 identifier를 보관하고, heartbeat/reconnect 없이 close-intent로 종료 의도를 전달하는가
- 같은 seam을 공유하는 WHIP/HTTP transport가 어떤 지점에서 갈라지는가 ([03. project_architecture.md §4](./03.%20project_architecture.md))
